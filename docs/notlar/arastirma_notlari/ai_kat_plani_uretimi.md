# AI-driven residential floor plan (kat planı) generation: state of the art 2025–2026 and applicability to a 37-model prefab catalog (PortatifEv)

Scope note: notes are in English; Turkish terms kept where useful (kat planı = floor plan, pano = wall panel, aks = grid axis, bayi = dealer, ön onay = pre-approval). Dates: "2026" items are the current state; anything 2020–2023 is marked as older baseline work. All numbers are as reported by the cited sources; where sources conflict this is flagged.

---

## Key Question 1 — Which generative approaches exist (graph/GAN, diffusion, transformer/LLM, LLM+solver), what inputs and datasets do they need, and how good are outputs?

### Takeaway
Four families exist: (a) older graph/GAN models (Graph2Plan, House-GAN++, 2020–21) that need a boundary and/or a room adjacency graph ("bubble diagram") and output raster masks or boxes; (b) diffusion models (HouseDiffusion 2023 and its 2025–26 descendants) that output vector room polygons but still leak overlaps/gaps and generalise poorly outside RPLAN; (c) LLM/transformer methods (Tell2Design 2023, HouseLLM 2024, FPDS 2025, HypergraphFormer 2026, RLVR-LLM 2026) that take text and emit JSON/sequence representations; and (d) 2025–26 hybrids that pair an LLM with an integer-programming solver, a diffusion refiner, or deterministic rule engines. Practically every method is trained on RPLAN (~80k Asian apartment plans, raster, Manhattan geometry); none of the research systems is production-ready as-is, and the strongest recent results all come from adding a verifier/solver around the neural model.

### Cited Findings

**Datasets (what everything is trained on)**
- RPLAN ≈ 80,000 single-unit residential plans, raster 256×256, rectangular rooms; CubiCasa5K = 5,000 plans (raster + SVG, with furniture); MSD (Modified Swiss Dwellings) = 5,372 plans / 18.9k units, vector + graph, multi-unit building floors; LIFULL ≈ 5,000,000 raster images, "mostly unvectorized/unannotated" — [ResPlan paper, related-work table](https://web3.arxiv.org/pdf/2508.14006)
- ResPlan (Aug 2025, Indiana University) = 17,000 residential plans extracted from public real-estate listing documents (CAD/PDF) into vector + graph form with walls, doors, windows, balconies, room types, interior/exterior/party walls; released under a permissive open-source licence with a Python pipeline on GitHub — [ResPlan](https://web3.arxiv.org/pdf/2508.14006)
- MSD was introduced because RPLAN "lacks some real-world design-related characteristics" (single apartments only, no elevation/furniture); MSD contains 5,372 curated plans from high-quality residential buildings — [Mostafavi et al., IJAC 2025](https://journals.sagepub.com/doi/10.1177/14780771241290649); dataset page — [4TU MSD](https://data.4tu.nl/datasets/e1d89cb5-6872-48fc-be63-aadd687ee6f9); CubiCasa5K repo — [GitHub](https://github.com/CubiCasa/CubiCasa5k)
- Graph2Plan reports that in RPLAN "over 93% of rooms" are representable as a single bounding box clipped by the building boundary — [Graph2Plan, ACM TOG 2020](https://ar5iv.labs.arxiv.org/html/2004.13204)
- Tell2Design (ACL 2023, Area Chair Award) is the reference dataset/benchmark for language-guided floor plan generation; official repo exists — [ACL Anthology](https://aclanthology.org/2023.acl-long.820/); [GitHub](https://github.com/LengSicong/Tell2Design). FPDS (2025) uses Tell2Design as its language-conditioned benchmark — [FPDS, eCAADe 2025](https://conf.dap.tuwien.ac.at/preprints/ecaade2025/ecaade2025_128.pdf)

**(a) Graph/GAN family — OLDER (2020–2021), still the standard baselines**
- Graph2Plan (ACM TOG 39(4), 2020): inputs = building boundary (128×128 binary image) + layout graph (room types, locations, sizes, adjacencies); outputs = raster plan (128×128) plus initial and refined room bounding boxes; it *retrieves* candidate layout graphs from RPLAN by user constraints and boundary similarity (turning-function distance), lets the user edit the graph, then generates; architecture = GNN + CNN + cascaded refinement + BoxRefineNet; limitation: one bounding box per room cannot capture all room shapes — [Graph2Plan](https://ar5iv.labs.arxiv.org/html/2004.13204); [ACM DL](https://dl.acm.org/doi/abs/10.1145/3386569.3392391)
- House-GAN++ (CVPR 2021): input = bubble diagram; output = raster room/door segmentation; iterative refinement where "a previously generated layout becomes the next input constraint"; authors claim outputs "competitive against the ground-truth floorplans, designed by professional architects" — [House-GAN++ project page](https://ennauata.github.io/houseganpp/page.html); [CVPR 2021 PDF](https://openaccess.thecvf.com/content/CVPR2021/papers/Nauata_House-GAN_Generative_Adversarial_Layout_Refinement_Network_towards_Intelligent_Computational_Agent_CVPR_2021_paper.pdf)
- A 2026 survey characterises HouseGAN/HouseGAN++/Graph2Plan as "single-pass systems with no post-generation validation" — [Kavya et al., Apr 2026](https://www.researchgate.net/publication/404175181_Intelligent_Architectural_Floor_Plan_Generation_From_Deep_Generative_Models_to_Multi-Agent_LLMs)

**(b) Diffusion family (2023 → 2026)**
- HouseDiffusion (arXiv Nov 2022 / CVPR 2023): input = graph-conditioned spec (bubble diagram); output = vector polygon loops of room/door corners; denoises 2D corner coordinates with both continuous and discrete objectives to enforce parallelism/orthogonality; can generate non-Manhattan layouts and control corner count per room; trained on RPLAN; **code/paper licence CC BY-NC-SA 4.0 (non-commercial)** — [arXiv 2211.13287](https://arxiv.org/abs/2211.13287); [CVPR 2023 PDF](https://openaccess.thecvf.com/content/CVPR2023/papers/Shabani_HouseDiffusion_Vector_Floorplan_Generation_via_a_Diffusion_Model_With_Discrete_CVPR_2023_paper.pdf); [GitHub](https://github.com/aminshabani/house_diffusion)
- Failure mode of HouseDiffusion reported by a later paper: it generates "gaps or holes within houses" and misaligned placement — [HouseLLM](https://arxiv.org/html/2411.12279v2)
- Boundary-Constrained Diffusion (Univ. Pisa / H&M, arXiv Feb 2026, 2602.01949): extends HouseDiffusion with a Boundary Cross-Attention module so the user's building perimeter polygon conditions generation; inputs = room adjacency matrix + boundary polygon + guidance scale; RPLAN 80k; boundary compatibility 0.04, FID 10.74 vs HouseDiffusion 10.35, graph compatibility 1.73; **diversity collapsed from 52.69 to 33.59 across training** (mode collapse); on a synthetic OOD set with pentagonal rooms FID = 290.0, i.e. "limited ability to reason about novel architectural styles" because corner counts are sampled from training histograms — [arXiv 2602.01949](https://arxiv.org/html/2602.01949v1)
- CE2EPlan (Univ. Zurich, arXiv Feb 2026, 2602.20377): end-to-end vector diffusion with a Graph-Attention Transformer, four interaction modes (automatic / room types / types+locations / partial completion), geometry-alignment losses to reduce overlaps and boundary violations; RPLAN split 56k/12k/12k; FID 1.08 (= DiffPlanner 1.08), GED 3.48 vs 3.54; limitations: **axis-aligned boxes only (Manhattan, no L-shaped rooms), rule-based post-alignment still required**, diversity drops as constraints increase, residential-unit scale only — [arXiv 2602.20377](https://arxiv.org/pdf/2602.20377)
- ChatHouseDiffusion (Oct 2024): LLM interprets natural-language prompts, Graphormer encodes topology, diffusion generates and *edits* plans; claims higher IoU than prior work and localized edits "without the need for complete redesigns"; the abstract does not name the LLM, backbone or numbers — [arXiv 2410.11908](https://arxiv.org/abs/2410.11908)
- Other 2024–25 diffusion works exist but were not fetched in detail: "Residential floor plans: Multi-conditional automatic generation using diffusion models" (Automation in Construction 2024) — [ScienceDirect](https://www.sciencedirect.com/science/article/abs/pii/S0926580524001109); "Floorplan-Diffusion … Pre-trained Large Latent Diffusion Model" (ICMR 2025) — [ACM DL](https://dl.acm.org/doi/10.1145/3731715.3733343)

**(c) Transformer / LLM family (text → structured layout)**
- LayoutGPT (NeurIPS 2023; OLDER): represents layouts in a CSS-like "style sheet language" and prompts an LLM; targets 2D image layouts and 3D indoor scenes (furniture), not architectural floor plans; claims 20–40% gains over text-to-image systems and "comparable performance as human users … for numerical and spatial correctness" — [arXiv 2305.15393](https://arxiv.org/abs/2305.15393)
- HouseLLM (arXiv 2411.12279, v2): Phase 1 GPT-4 with chain-of-thought emits JSON `Room_i = {name, style, position(X,Y), size(w,h), door(direction)}`; Phase 2 a conditional diffusion model refines it, conditioning during both noising and denoising; RPLAN, 5–8-room groups; FID 7.5 vs HouseDiffusion 10.3 (28% better), compatibility 0.25 vs 1.2 (79% better), realism −0.03 vs −0.19; **Layout-LLM alone produces "many overlapping rooms" and cannot enforce fine-grained spatial constraints** — [HouseLLM](https://arxiv.org/html/2411.12279v2)
- FloorPlan-DeepSeek / FPDS (eCAADe 43, 2025; Tsinghua, 9 authors): "next room prediction" — plan encoded as a sequence of rooms (type, centre x/y, width, height); primary model FloorPlan-DeepSeek-R1-32B; inputs = text, partial plan, building outline; three auxiliary constraints (functional adjacency, editability, outline-boundary so rooms do not exceed the outline); FID 16.465, PSNR 76.564, SSIM 0.934; compared with Obj-GAN, Tell2Design, GLM-4-9b-chat, Qwen2.5-VL-72B; limitations: "local spatial mismatches despite acceptable accuracy", robustness under complex semantics, single-unit scale — [FPDS preprint](https://conf.dap.tuwien.ac.at/preprints/ecaade2025/ecaade2025_128.pdf); [arXiv 2506.21562](https://arxiv.org/abs/2506.21562)
- LLM-based framework for automated and customized floor plan design (Automation in Construction vol. 180, Dec 2025, Qiu et al., DOI 10.1016/j.autcon.2025.106512): dual LLM — a *recognition* model that turns existing plans into natural-language descriptions (data augmentation via a syntax-tree representation) and a *generation* model producing vectorized plans; LoRA rank 32, 4 epochs, A100 40GB; relies on manually annotated seed data; "limitations in accounting for subjective design criteria" — [ScienceDirect](https://www.sciencedirect.com/science/article/abs/pii/S0926580525005527)
- HypergraphFormer (arXiv 18 May 2026): LoRA-fine-tuned Qwen3 outputs a JSON hypergraph = binary-space-partition tree + access (door) graph, i.e. an abstract, boundary-free decomposition that is then **instantiated procedurally against any user boundary**, with procedural edits (add/remove rooms, rotate/reflect, gradient-descent room-area refinement) without retraining; trained on RPLAN access-graph→hypergraph pairs; OOD test set WMR24 (architect-designed plans); GED 1.62 vs HouseDiffusion 1.95 vs HouseGAN++ 2.59; strict access-graph accuracy 40.9% vs 6.0% / 16.3%; room multiset accuracy 100% vs 44.2% / 96.7% — [arXiv 2605.18932](https://arxiv.org/html/2605.18932v1)
- Generative Floor Plan Design with LLMs via RL with Verifiable Rewards (arXiv 2605.14117, May 2026): Llama-3.3-70B-Instruct, SFT + GRPO with deterministic verifiable rewards; input = bubble diagram + JSON spec (room sizes, total area); output = JSON polygons in metric units "compatible with CAD software"; RPLAN 80,788 plans converted to JSON; 8-room task: compatibility (GED) 0.15 vs 2.5 for HouseDiffusion (94% reduction), overlap 0.13, FID 7.0 vs 9.5, realism 0.03 (40-person study), room-area deviation ≈10–12% from requested — [arXiv 2605.14117](https://arxiv.org/html/2605.14117v1). Venue is inconsistent across sources: a NeurIPS 2025 virtual page lists it — [neurips.cc](https://neurips.cc/virtual/2025/136642) — while a third-party note files it under ACL 2026 — [papernotes](https://en.papernotes.org/ACL2026/llm_nlp/generative_floor_plan_design_with_llms_via_reinforcement_learning_with_verifiabl/)

**(d) LLM + solver / rule-engine hybrids (2025–2026)** — see also Key Question 4
- Co-Layout (arXiv 2511.12474 v2, Mar 2026): LLM agent workflow converts text into structured room/furniture constraints; a **grid-based integer program** (floor discretised into cells, "Modulor"-inspired) then solves rooms and furniture jointly, coarse-to-fine; hard constraints = non-overlap (each cell exactly one owner), flow-based corridor connectivity, room accessibility, adjacency, big-M axis-aligned boxes; motivation: LLMs' "inability to generate interior designs with precise coordinates, often resulting in conflicts within the output" — [Co-Layout](https://arxiv.org/html/2511.12474v2)
- Multi-agent orchestration with deterministic rule engines (Indian codes + Vaastu), Apr 2026: nine agents in three phases, 120 test prompts, **80.2% constraint satisfaction vs 74.4% for single-shot GPT-4o (+5.8 pp)**, 47% cheaper inference via mixture-of-experts routing; open problems: LLMs "handle rectangular plots well but fail on L-shaped or trapezoidal configurations", rule coverage gaps, no structural validation — [Kavya et al. 2026](https://www.researchgate.net/publication/404175181_Intelligent_Architectural_Floor_Plan_Generation_From_Deep_Generative_Models_to_Multi-Agent_LLMs)

**Evaluation problems (why "metrics" understate real failure)**
- Mostafavi et al. (IJAC 23(2), 2025) found AI-generated plans (U-GCN, modified HouseDiffusion on MSD) perform "on average half as well" as ground truth; models capture high-level attributes (unit differentiation, typology) but "struggled capturing" room proportions and topology; expert agreement was weak (Cohen's kappa largely negative), i.e. evaluation is "highly subjective" and architecture-specific metrics are missing — [IJAC 2025](https://journals.sagepub.com/doi/10.1177/14780771241290649)
- A 2025 GenAI survey notes "the lack of appropriately diverse, high-quality, and specially designed datasets regarding floor planning", "high implementation costs", and that systems "struggle in complicated architecture projects, when human skill is still important" — [GenAICHI 2025 survey](https://generativeaiandhci.github.io/papers/2025/genaichi2025_6.pdf)
- Standard metrics used across the field: FID (realism/diversity of rasterised output), Compatibility / Graph Edit Distance between requested and produced adjacency graph, overlap ratio, boundary compatibility, human realism studies — as used in [HouseLLM](https://arxiv.org/html/2411.12279v2), [RLVR paper](https://arxiv.org/html/2605.14117v1), [Boundary-Constrained Diffusion](https://arxiv.org/html/2602.01949v1), [HypergraphFormer](https://arxiv.org/html/2605.18932v1)

**Modular / prefab-specific research**
- Ghannad & Lee (Automation in Construction 139, Jul 2022): CoGAN generates layout images, then a "module configuration algorithm" vectorises and "structurally modularize[s]" the generated layout against manufacturing/transport constraints (volumetric modules), with BIM-based compliance checks; dataset size not disclosed — [ScienceDirect](https://www.sciencedirect.com/science/article/abs/pii/S0926580522001078)
- Related titles exist but were not fetched: "Intelligent floor plan design of modular high-rise residential building based on graph-constrained GANs" (Automation in Construction 2023) — [ScienceDirect](https://sciencedirect.com/science/article/pii/S0926580523005241); "A genetic algorithm application for automatic layout design of modular residential homes" — [Academia](https://www.academia.edu/29158231/A_genetic_algorithm_application_for_automatic_layout_design_of_modular_residential_homes); classic exhaustive enumeration of rectangular floor plans on a grid — [CACM](https://dl.acm.org/doi/10.1145/358800.358804)

### Inferences
- Every strong 2025–26 result is on RPLAN (Chinese apartment stock, Manhattan geometry, no verandas/porches, no panel modules). A Turkish single-storey prefab with a front veranda is out-of-distribution for all of them; the boundary-constrained diffusion paper's OOD collapse (FID 290) and the domain-shift paper (Q5) suggest a raw pretrained model would not transfer without retraining.
- The research trend line is unambiguous: pure neural generation → neural generation + hard-constraint post-processing → LLM emitting an *abstract* structure (graph/BSP/JSON) that a deterministic step instantiates. The last form is the closest to what a 125.5 cm aks grid needs, because the geometry step can be made to snap to the grid by construction.
- Reported "overlap 0.13" or "compatibility 0.15" are averages over RPLAN test cases; none of the papers reports a per-plan "valid for construction" pass rate, so a company should assume a non-trivial fraction of raw outputs need correction.
- Licensing matters: HouseDiffusion's code is non-commercial (CC BY-NC-SA); several other codebases and RPLAN itself are research-oriented. A company cannot assume it can ship these models.

### Gaps
- Exact size and construction details of Tell2Design (number of text–plan pairs, human vs. synthetic descriptions) were not verified from a fetched primary page.
- House-GAN++ numeric metrics and its exact RPLAN subset were not recoverable from the fetched project page.
- ChatHouseDiffusion's LLM, backbone and quantitative results are not in its abstract; the full paper was not fetched.
- No paper was found that reports a "percentage of generated plans that pass a deterministic buildability check" (non-overlap + every room has a door + all rooms inside boundary) for frontier models or diffusion models in a directly comparable way; overlap/GED averages are the closest proxies.
- RPLAN licence terms (research-only by request, to my recollection) were not verified in this research.

## Key Question 2 — Commercial / production tools: what they generate, APIs, pricing, modular support

### Takeaway
No commercial tool found is built for single-storey panelised houses on a fixed module grid, and none exposes a cheap public "text → DXF house plan" API. The closest fits are Maket (consumer/pro plan generator with DXF/PDF export; API only on a custom-priced "Scale" tier) and Finch (constraint-based plan generation, but the AI generation and "firm plan library" features are Enterprise at €14,500/yr for ≥3 seats). TestFit, Forma, Archistar and Hypar are site/massing/multifamily/commercial tools; Higharc is the only vendor training a production model on homebuilder BIM data, and it is a platform for US production builders, not a purchasable component.

### Inferences
- For PortatifEv the only off-the-shelf candidates with DXF output and an API path are Maket (Scale tier, custom price; "custom generation models" would in theory allow training on the 37 catalog plans but capability is unverified) and possibly Finch Enterprise (€14.5k/yr, ≥3 seats, "firm-wide plan library"). Both are priced/positioned for architecture firms rather than a small dealer-facing sales process.
- None of these tools knows about a 125.5 cm pano grid; any output would need a post-processing "snap-to-aks" step and re-validation, which erodes the benefit of buying a generator.
- TestFit's MCP add-on (2026) is an early signal that AEC vendors are exposing generative tools to LLM assistants; but TestFit generates site plans/unit mixes, not house interiors.
- Higharc's GBM shows what a *production-grade* homebuilder model requires: thousands of real BIM homes and constraints baked into the representation — far beyond a 37-plan catalog.

- Whether Finch's "AI-powered floor plan generation" works for detached single-storey houses (vs. multi-unit residential) is not stated on its site.
- "Plantly" could not be identified; may be a misremembered name or a very small product.
- Whether any vendor supports modular/panelised construction constraints: no evidence found (TestFit, Finch, Maket, Forma pages contain no such mention).
- Autodesk Forma per-seat pricing and API pricing were not captured.

## Key Question 3 — Can frontier LLMs (GPT-4.1/GPT-5/o-series, Claude, Gemini 2.5) reliably produce geometrically valid floor plans directly? What do evaluations of LLM spatial reasoning say?

### Takeaway
No. Across 2024–2026 evidence, frontier LLMs asked to emit coordinates directly produce overlapping rooms, gaps, misaligned furniture and invalid adjacencies at a non-negligible rate; dedicated benchmarks (FloorplanQA Oct 2025, Blueprint-Bench Sep 2025) show even reasoning models (GPT-5, o-series-class, Gemini 2.5 Pro, Claude Sonnet/Opus 4) fall below 50% on free-space/max-rectangle tasks and at or below random on photo-to-plan reconstruction. LLMs are, however, reliable at *parsing intent* into structured requirement JSON and at *choosing among* candidates — which is the role the literature now assigns them.

### Cited Findings
- FloorplanQA (arXiv 2507.07644 v2, Oct 2025): 2,000 layouts / 16,000 questions in JSON/XML over kitchens, living rooms, bedrooms and HSSD scenes; eight task types (distance, view angle, placement feasibility, free space, visibility, max-rectangle fitting, repositioning, collision-free path); models: GPT-5, GPT-5-mini, GPT-OSS-120B/20B, DeepSeek-R1, Gemini 2.5 Flash, Qwen3-30B-Thinking, Claude Sonnet 4, GPT-4.1/-mini, Qwen3 235B/30B/Coder-480B, Kimi-K2, Devstral; **85–99% on simple pair-distance tasks, but "very low accuracies" on free-space and max-box tasks; reasoning models improve yet "remain below 50%"**; weaknesses on non-axis-aligned polygons, unions of overlapping objects, rotations, multi-step path planning; conclusion: "current LLMs lack sufficiently robust internal geometric representations for complex spatial inference", recommending hybrid approaches with external geometric solvers — [FloorplanQA](https://arxiv.org/html/2507.07644v2)
- Blueprint-Bench (Andon Labs, arXiv 2509.25229, 24 Sep 2025): 50 apartments × ~20 photos → 2D plan; models GPT-5, Claude 4 Opus, Gemini 2.5 Pro, Grok-4, GPT-Image, NanoBanana, Codex CLI, Claude Code; score = edge overlap 50% + degree correlation 20% + density 10% + room count 10% + door count 5% + door orientation 5%; **"Most models perform at or below a random baseline, while human performance remains substantially superior"**; GPT-5 and Gemini 2.5 Pro statistically above random; iterative agent refinement gave "no meaningful improvement over single-pass generation"; image models ignored instructions — [Blueprint-Bench](https://arxiv.org/html/2509.25229)
- HouseLLM: GPT-4 with chain-of-thought as sole generator yields "many overlapping rooms" and cannot enforce fine-grained spatial constraints, which is why a diffusion refinement phase is added — [HouseLLM](https://arxiv.org/html/2411.12279v2)
- Co-Layout: "one significant limitation of LLMs is their inability to generate interior designs with precise coordinates, often resulting in conflicts within the output" — [Co-Layout](https://arxiv.org/html/2511.12474v2)
- Text-to-Layout (Univ. of Houston / UT Austin, arXiv 2509.00543, 2025): tested GPT-4o, o4-mini, o4-mini-high, Claude 2.1, Gemini 2.5 Pro; "GPT-4o consistently produced the most reliable and well-structured outputs"; LLM emits JSON of walls/doors/windows as start–end coordinates plus furniture centres, then LLM-written Python for the Revit API builds geometry; documented failures: over-partitioning with poor circulation, unzoned spaces, overcrowded layouts with illogical adjacencies, misaligned furniture, insufficient clearances; needed a greedy wall-seeking repair algorithm (δ = 1 ft clearance), room validation, door/window verification and grid-based path-finding; results came from "hundreds of testing cycles" on a single 30×40 ft case; ~10 min per run on a laptop; no quantitative success rate, no expert validation, no building-code compliance — [Text-to-Layout](https://arxiv.org/html/2509.00543v1)
- Multi-agent system vs single-shot GPT-4o: single-shot GPT-4o achieved 74.4% constraint satisfaction (80.2% − 5.8 pp) on 120 prompts; LLMs "handle rectangular plots well but fail on L-shaped or trapezoidal configurations" — [Kavya et al. 2026](https://www.researchgate.net/publication/404175181_Intelligent_Architectural_Floor_Plan_Generation_From_Deep_Generative_Models_to_Multi-Agent_LLMs)
- Analogous domain evidence (structural frames, not floor plans): general-purpose GPT-4o scored 0% and Gemini 2.5 Pro 37% on multi-step geometric model construction, while a checkpointed multi-agent pipeline with deterministic validators reached 90% — [Geng et al., Mar 2026](https://arxiv.org/html/2603.07728)
- RLVR paper: even after SFT + RL on 80k plans, a 70B Llama's requested-vs-delivered room areas deviate ≈10–12% and overlap is 0.13 (not zero) — [arXiv 2605.14117](https://arxiv.org/html/2605.14117v1)
- HypergraphFormer's design rationale: the LLM is not asked for coordinates at all — it emits a BSP tree + access graph and a procedural step instantiates geometry into any boundary — [HypergraphFormer](https://arxiv.org/html/2605.18932v1)

### Inferences
- A WhatsApp brief such as "80 m², 2+1, front veranda" is well within what an LLM can turn into a *requirements object* (area, room list, adjacencies, veranda flag). The risk is only in letting it invent coordinates; the literature consistently routes coordinates through a solver/procedure/refiner.
- Because FloorplanQA shows weakness precisely on "does this rectangle fit in the remaining free space?", an LLM should not be the component that decides whether a bathroom fits between two aks lines; that is a trivial integer check in code.
- Iterative "look at the picture and fix it" loops (Blueprint-Bench agents) did not help; loops help only when the checker is deterministic code that returns concrete violations (as in the multi-agent and structural papers).

### Gaps
- No 2026 benchmark was found that tests GPT-5 / Claude Opus 4.x / Gemini 3 specifically on *generating* (rather than reasoning over or reconstructing) residential floor plans with a deterministic validity pass rate; the closest are the 74.4% single-shot GPT-4o figure (Kavya et al.) and the qualitative HouseLLM/Text-to-Layout reports.
- Model versions in the papers lag: Text-to-Layout used Claude 2.1 (very old); no paper tested Claude 4-series or Gemini 3 as a plan generator.

## Key Question 4 — What architecture does the literature/practice recommend for reliability ("LLM as planner, solver/procedure as executor, validator in the loop")? Documented systems

### Takeaway
The converging pattern in 2025–2026 papers and in Higharc's production system is: (1) LLM normalises the natural-language brief into a structured spec; (2) a deterministic engine (integer program, procedural instantiation, retrieval/template, or constrained neural model) produces geometry; (3) deterministic validators (overlap, boundary, door access, code rules) check and either repair or send violations back for another iteration; (4) a human (architect / ön onay) signs off. Documented instances: Co-Layout (LLM → grid IP), HypergraphFormer (LLM → BSP/access graph → procedural instantiation + gradient refinement), the nine-agent Vaastu/code system (LLM agents + rule engines, +5.8 pp over single-shot), Text-to-Layout (LLM JSON → Revit script → greedy repair), HouseLLM (LLM JSON → diffusion refiner), RLVR (deterministic checkers used as training reward), FloorplanQA's explicit recommendation of external geometric solvers, and Higharc's GBM (constraints inside the representation, "no post-generation cleanup").

### Cited Findings
- Co-Layout: "LLM-based agent workflow converts textual user requirements into structured constraints", solved by a unified grid-based integer program with hard non-overlap, connectivity and accessibility constraints; coarse grids warm-start fine grids for "notable computational efficiency" — [Co-Layout](https://arxiv.org/html/2511.12474v2)
- HypergraphFormer: LLM outputs an abstract hypergraph; geometry is instantiated against "arbitrary boundaries"; edits (add/remove room, rotate/reflect, gradient-descent area refinement) are procedural and need no retraining; best OOD generalisation on architect-designed WMR24 — [HypergraphFormer](https://arxiv.org/html/2605.18932v1)
- Multi-agent orchestration (Apr 2026): specification normalisation → iterative compliance-driven refinement with deterministic rule engines → cost/furniture planning; 80.2% constraint satisfaction vs 74.4% single-shot GPT-4o; prior LLM layouts criticised because "LLM outputs are unvalidated. There is no mechanism to check whether a generated plan actually satisfies building codes"; traditional constraint programming criticised as needing "exhaustive manual rule encoding" — [Kavya et al. 2026](https://www.researchgate.net/publication/404175181_Intelligent_Architectural_Floor_Plan_Generation_From_Deep_Generative_Models_to_Multi-Agent_LLMs)
- Text-to-Layout: JSON intermediate → LLM-generated Revit Python → greedy feasibility repair → post-processing (room validation, door/window verification, grid path-finding for connectivity) — [Text-to-Layout](https://arxiv.org/html/2509.00543v1)
- HouseLLM: LLM layout → conditional diffusion refinement with constraints applied in both noising and denoising — [HouseLLM](https://arxiv.org/html/2411.12279v2)
- RLVR: verifiable (deterministic) rewards for graph compatibility, overlap and area accuracy used to train the LLM; output is metric JSON "compatible with CAD software" — [arXiv 2605.14117](https://arxiv.org/html/2605.14117v1)
- FloorplanQA authors recommend "near-term hybrid approaches integrating external geometric solvers" — [FloorplanQA](https://arxiv.org/html/2507.07644v2)
- Higharc GBM: constraints "enforced during creation rather than corrected afterward" via wall-referenced coordinates and encoder–decoder conditioning on the room's structural envelope — [Higharc](https://www.higharc.com/blog/ai-layout-at-higharc-tokenizing-buildings)
- Mostafavi et al.: keep "the designer in the loop" (late-stage expert evaluation or interactive fine-tuning), because "expert knowledge is a determining factor" — [IJAC 2025](https://journals.sagepub.com/doi/10.1177/14780771241290649)
- Structural-modeling analogue: embedded checkpoints (planning-stage and geometry-stage consistency checks) with up to 5 regeneration retries lifted accuracy to 90% and cut runtime 85% (949 s → 141 s) versus a sequential agent chain — [Geng et al. 2026](https://arxiv.org/html/2603.07728)
- Practitioner tooling: TestFit's MCP Connection lets an AI assistant "prompt directly editable site plans" — [TestFit](https://www.testfit.io/pricing); Maket separates "AI floor plan editing" from human-validated uploads and disclaims construction use — [Maket](https://www.maket.ai/ai-floor-plan-generator)

### Inferences
- For PortatifEv the executor should be *grid-native*: since walls sit on a 125.5 cm aks lattice, the plan is an integer tiling problem; a small integer program (as in Co-Layout) or a template-parameterisation with integer module counts is both simpler and more reliable than any neural generator, and validation (overlap, door per room, veranda on front edge, total m²) is exact arithmetic.
- The LLM layer earns its keep in three places: parsing dealer WhatsApp messages (Turkish, informal, incomplete), asking clarifying questions, and ranking/explaining candidates; it should never be the source of truth for coordinates.
- The documented gains from validation loops are moderate (+5.8 pp in the 120-prompt study) when the generator is an LLM; they are decisive when the generator is deterministic (validation becomes a guarantee rather than a filter).

### Gaps
- The ASCE Journal of Computing in Civil Engineering paper "A Multiagent Large Language Model–Based System for Early-Stage Building Layout Planning" (vol. 40 no. 6) exists but is paywalled; its numbers were not retrieved — [DOI](https://doi.org/10.1061/JCCEE5.CPENG-7723)
- No paper documents a WhatsApp/chat-fronted floor-plan pipeline; the chat channel is orthogonal to the generation engine and was not covered by any source found.
- None of the hybrid systems report end-to-end latency or cost per plan except Text-to-Layout (~10 min/run) and the multi-agent paper (47% cost reduction, absolute cost not given).

## Key Question 5 — With only 37 template plans: is training/fine-tuning feasible, and what is the realistic alternative (template adaptation, parametric variants, retrieval + rule-based modification)?

### Takeaway
Training or fine-tuning a generative floor-plan model on 37 plans is not supported by any evidence: published systems use 80k (RPLAN), 17k (ResPlan), 5.4k (MSD), ~3,500 homes / 75k rooms (Higharc), and the most data-efficient 2026 paper still needs 1,000 real plans on top of 135k synthetic ones, with models degrading "up to an order of magnitude" under domain shift. The realistic path is retrieval of the nearest catalog plan plus rule-based/parametric modification on the 125.5 cm aks grid — a pattern the literature already uses (Graph2Plan's retrieval step, ICCBR 2024 case-based reasoning with "transformational adaptation", HypergraphFormer's procedural instantiation, Co-Layout's grid IP) — with an LLM only for intent parsing and dialogue.

### Cited Findings
- Data scales actually used: RPLAN ≈ 80,000 (raster), ResPlan 17,000 (vector), MSD 5,372, CubiCasa5K 5,000 — [ResPlan](https://web3.arxiv.org/pdf/2508.14006); RLVR fine-tuning used 80,788 RPLAN plans — [arXiv 2605.14117](https://arxiv.org/html/2605.14117v1); CE2EPlan trained on 56k — [arXiv 2602.20377](https://arxiv.org/pdf/2602.20377); Higharc's production model used ≈3,500 homes / 75,720 rooms of real BIM data — [Higharc](https://www.higharc.com/blog/ai-layout-at-higharc-tokenizing-buildings)
- Domain shift is severe: cross-dataset transfer shows "up to an order of magnitude performance degradation" because of "distinct architectural cultures and spatial constraints"; the proposed remedy is pre-training on 135k procedurally generated synthetic layouts (physically valid but "deliberately sacrificing architectural realism") then fine-tuning; **smallest real-data regime tested = 1,000 plans**, giving e.g. 18.8 vs 30.8 MPE (39% better) RPLAN→MagicPlan and 7.05 vs 12.1 MPE (41.7%) on a vertex-level diffusion model; authors (Homiwoo / École Polytechnique, Jul 2026) frame this as help for "organizations lacking large annotated floor plan datasets for their target regions" — [arXiv 2607.06483](https://arxiv.org/html/2607.06483)
- The Automation-in-Construction LLM framework had to *manufacture* its training corpus by having a recognition LLM describe existing plans, because manual annotation was the bottleneck; training still used LoRA on an A100 40GB — [ScienceDirect](https://www.sciencedirect.com/science/article/abs/pii/S0926580525005527)
- Diffusion models "sample room corner counts from training histograms" and fail on unfamiliar geometries (FID 290 on novel synthetic set) — [arXiv 2602.01949](https://arxiv.org/html/2602.01949v1)
- Retrieval + adaptation is an established pattern: Graph2Plan retrieves candidate layout graphs from the plan database by user constraints and boundary similarity (turning-function distance) before generation — [Graph2Plan](https://ar5iv.labs.arxiv.org/html/2004.13204); Eisenstadt, Langenhan, Bielski, Bergmann, Althoff (ICCBR 2024, DFG Metis-II project): subgraph matching retrieves the nearest floor plan by room graph, then "transformational adaptation" uses retrieved cases as templates to complete/modify designs, validated with a user study of architecture-domain representatives — [Springer](https://link.springer.com/chapter/10.1007/978-3-031-63646-2_21); earlier work by the same group: "Generation of Floor Plan Variations with CNNs and Case-based Reasoning" (2019) — [Semantic Scholar](https://www.semanticscholar.org/paper/Generation-of-Floor-Plan-Variations-with-Neural-and-Eisenstadt-Langenhan/bb844e9748dafcc2df260242a7f902a5f6ba0d0f); BIM-based variant retrieval with CBR and pattern matching — [Emirates Scholar](https://www.emiratesscholar.com/bim-based-variant-retrieval-of-building-floor-plans-using-case-based-reasoning-cbr-and-pattern-matching-pm/)
- Procedural/parametric instantiation of an abstract plan into an arbitrary boundary, with add/remove-room and rotate/reflect operations and gradient-based area tuning, is exactly how HypergraphFormer achieves editability without retraining — [HypergraphFormer](https://arxiv.org/html/2605.18932v1)
- Grid-based exact optimisation of room layouts (each cell owned by exactly one room, connectivity as a flow, adjacency constraints, coarse-to-fine) is demonstrated by Co-Layout — [Co-Layout](https://arxiv.org/html/2511.12474v2); exhaustive enumeration of rectangular plans on a grid is a classic result — [CACM](https://dl.acm.org/doi/10.1145/358800.358804)
- Modular housing pipelines in the literature post-process generated layouts through a "module configuration algorithm" against manufacturing/assembly constraints, i.e. modularisation is a deterministic step after (or instead of) generation — [Ghannad & Lee 2022](https://www.sciencedirect.com/science/article/abs/pii/S0926580522001078)
- Vendor routes for small catalogs: Maket Pro offers "custom templates" and Scale offers "custom generation models" (custom pricing) — [Maket pricing](https://www.maket.ai/pricing); Finch Enterprise offers a "firm-wide plan library" and generation using "your firm's design system" — [Finch pricing](https://www.finch3d.com/pricing)
- Operational burden signals: research pipelines needed an A100 for LoRA training — [ScienceDirect](https://www.sciencedirect.com/science/article/abs/pii/S0926580525005527); Text-to-Layout depended on Revit + Python shell and "manually crafted prompt templates", ~10 min per run — [Text-to-Layout](https://arxiv.org/html/2509.00543v1); HouseDiffusion code is non-commercial (CC BY-NC-SA 4.0) — [arXiv 2211.13287](https://arxiv.org/abs/2211.13287); the nine-agent system needed manual encoding of every code rule (only 14 Vaastu rules, 4 jurisdictions) — [Kavya et al. 2026](https://www.researchgate.net/publication/404175181_Intelligent_Architectural_Floor_Plan_Generation_From_Deep_Generative_Models_to_Multi-Agent_LLMs)

### Inferences
- 37 plans is roughly 0.05% of RPLAN and ~4% of the smallest "data-efficient" regime tested (1,000); fine-tuning any diffusion/GAN/LLM generator on them would at best memorise the catalog and at worst hallucinate invalid geometry, with no evidence base to predict behaviour. Synthetic pre-training (135k procedurally generated plans) would require building the procedural generator anyway — at which point the procedural generator *is* the product.
- The 125.5 cm module makes a template/parametric approach unusually tractable: every catalog plan is an integer configuration of pano units (e.g., an 8×6-module rectangle is 10.04 m × 7.53 m ≈ 75.6 m²; 9×6 is 11.30 m × 7.53 m ≈ 85.0 m²), so "80 m², 2+1, front veranda" maps to a small enumerable space of module counts, and dealer requests "not in the catalog" are typically ±1 module stretches, room swaps, or veranda additions to an existing template (arithmetic on the catalog, not generation).
- Recommended concrete stack, consistent with the cited systems: (1) LLM (any frontier API) parses the WhatsApp brief into a JSON spec and asks follow-ups; (2) retrieval scores the 37 DXF-derived templates by spec similarity (room multiset, area, orientation, veranda); (3) parametric/grid rules stretch or edit the nearest template in whole-module steps, or a small integer program places rooms on the aks grid when no template is close; (4) deterministic validators (non-overlap, boundary, door per room, min room sizes, panel counts) gate output; (5) DXF→PDF rendering with a visible "ön onay — not for construction" stamp; (6) architect review before quotation. This is the "LLM as planner, solver as executor" pattern documented above, and needs no GPU or model training.
- The DXF catalog is a hidden asset: a one-time conversion of 37 DXF files into a structured template format (rooms as module-count rectangles + adjacency + door/window slots) is the real engineering work; it is comparable in spirit to Higharc's BIM tokenisation but at catalog scale rather than model-training scale.
- Honest complexity note: even the deterministic approach requires a developer to build and maintain the parser, template rules and validators; a non-developer-led company should budget for an external developer or an integrator, but not for ML training infrastructure.

### Gaps
- No published case study was found of a prefab/modular house company deploying LLM-fronted plan generation on a small proprietary catalog; the recommendation above is an inference from the cited research patterns, not a documented deployment.
- No source quantifies the minimum number of plans at which fine-tuning starts to beat retrieval + rules; the 1,000-plan figure is the smallest tested, not a threshold.
- Turkish regulatory requirements for pre-approval drawings (what a "ön onay" plan must contain) were out of scope and not researched.
- Costs of LLM API usage per WhatsApp dialogue and of WhatsApp Business API integration were not researched (outside the generation-engine scope).

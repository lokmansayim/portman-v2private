# Rule- and Constraint-Based Generation of Small-House Floor Plans on a Modular Panel Grid (non-ML path) and Prefab Product-Configurator Practice — as of September 2026

Scope reminder for the writer: the company builds small prefabricated houses (30–120 m², 1+0 to 4+1, optional veranda, gable roof) whose walls are panels on a fixed 125.5 cm module; 37 catalog plans exist as CAD/DXF; a Python engine (ezdxf + Shapely + PyMuPDF) already draws plans from a JSON "İş Emri" (work order) with rooms as rectangles in module units. The goal is a "serbest yerleşim üretici" (free-layout generator) that takes a room program + outer dimensions (or m²) and returns a valid plan under company rules, plus validation, and a path to turn the 37 templates into a parametric family. All of this must run in Python on a small VPS (no GPU).

## Key Question 1 — Constraint programming / MILP / SAT, metaheuristics and shape grammars for grid-based room layout (with formulation sketches and runtimes for small grids)

### Takeaway
For a house of 5–9 rooms on a 6×8 to 8×10 module grid, an exact CP-SAT model (rooms as integer rectangles, `AddNoOverlap2D`, exact-tiling coverage, adjacency via enforcement literals, exterior-wall requirement for windowed rooms) solves to proven optimality in well under a second on a 2-vCPU box; the hard part is not solving but scoring/ranking the thousands of legal tilings, which is why the literature pairs exact solvers with either a GA/heuristic "cell shuffle" (Laignel 2021), an LLM-written constraint set (Co-Layout 2025/26) or template guidance. Doors/windows are almost always post-processed, not solved.

### Cited Findings

**Grid/cell-assignment integer programming (2025–2026)**
- Co-Layout (Nov 2025; listed as AAAI 2026) formulates layout as grid-based integer programming: binary `x_{i,j}^k` (cell (i,j) belongs to room k), `p_{i,j}` (corridor cell), with spatial exclusivity `p_{i,j} + Σ_k x_{i,j}^k = 1`, flow-based corridor connectivity (flow variables per cardinal direction with conservation/capacity), room accessibility via auxiliary access-point literals bordering corridor cells, room adjacency via auxiliary `β_{i,j}^{k,m}` requiring at least one shared boundary, and big-M axis-aligned bounding-box constraints; the objective is a weighted sum of rectangularity, perimeter, area target, aspect ratio, privacy hierarchy and furniture terms — [Co-Layout arXiv 2511.12474 (PDF)](https://arxiv.org/pdf/2511.12474)
- Co-Layout uses a coarse-to-fine strategy (e.g., 6×5 grid then 12×10 grid; 2×2 down-sampling gives a "75%" reduction in problem scale), the grid unit is one "Modulor" module, the solver is Gurobi v12 on an 8-core Ryzen with 16 GB RAM, and the discretized problem "involves thousands of integer variables"; positions of doors and windows "are not optimization variables; instead, they are determined via post-processing" (doors prioritised on wall segments adjacent to corridors/open areas, windows on exterior walls avoiding furniture); exact per-case runtimes in seconds are not given in the main paper — [Co-Layout arXiv 2511.12474 (PDF)](https://arxiv.org/pdf/2511.12474)
- Co-Layout's abstract: the LLM extracts structured constraints from text, integer programming solves the spatial problem; the formulation "accounts for key design requirements, including corridor connectivity, room accessibility, spatial exclusivity, and user-specified preferences" — [Co-Layout arXiv abstract](https://arxiv.org/abs/2511.12474)

**Constraint programming + genetic refinement (2021)**
- Laignel, Pozin, Geffrier, Delevaux, Brun and Dolla (Automation in Construction, 2021) discretize the floor space into a grid "according to architectural constraints", turn layout into a cell-assignment problem solved by constraint programming (non-overlap, adjacency, target areas, circulation), select three differentiated candidates, insert corridors, then run a genetic-algorithm "final cell shuffle"; solutions are "mostly generated in about 1 min"; the study used 62 training and 19 validation apartment–specification pairs; the CP solver brand is not stated in the abstract — [Laignel et al. 2021, ScienceDirect](https://www.sciencedirect.com/science/article/abs/pii/S0926580520310712)

**MILP grid layout with open code (2020)**
- GRIDS (Dayama, Todi, Saarelainen, Oulasvirta, CHI 2020) uses a mixed-integer linear program for grid layouts with objectives for alignment, rectangularity of the overall composition and preferred placement; it generates multiple diverse solutions, supports auto-completion of partial designs, and the engine is open source at github.com/aalto-ui/grids — [GRIDS project page](https://kashyaptodi.com/grids/)

**Stochastic optimization / Bayesian program synthesis (2010)**
- Merrell, Schkufza and Koltun (ACM TOG 29(6), SIGGRAPH Asia 2010): "Given a set of high-level requirements, an architectural program is synthesized using a Bayesian network trained on real-world data. The architectural program is realized in a set of floor plans, obtained through stochastic optimization"; rooms/relations are represented as bubble diagrams and the floor-plan cost function has terms for interior/exterior shape cohesion and program realization — [Koltun publication page](https://vladlen.info/publications/computer-generated-residential-building-layouts/)

**Survey of the field (2025)**
- The 2025 review "Computer-Aided Layout Generation for Building Design" (Liu et al.) groups optimization-based methods into bottom-up (Merrell 2010 Bayesian networks; GPLAN graph-theoretic dimensioned floorplans; Guo et al. evolutionary multi-agent) and top-down (Medjdoub 2000 subdivision with adjacency/scale constraints; Banerjee 2008 interactive), with key techniques "integer/mixed-integer programming (Wu et al., 2013), simulated annealing, Bayesian networks, MCMC, genetic algorithms"; it credits optimization methods with "guaranteed constraint satisfaction" and designer control, but "limited diversity", need for manual refinement and "domain-specific hand-crafted guidelines", while learning-based methods (RPLAN, Graph2Plan, HouseGAN++, HouseDiffusion, MaskPlan) show "incorrect arrangement of elements and the presence of generated artifacts", poor cross-dataset generalisation, and even the SOTA HouseDiffusion has "noticeable issues" including door placement errors — [Liu et al. 2025 review (CVMJ PDF)](https://iccvm.org/2025/papers/s7p5-532-cvmj.pdf)

**Graph-theoretic exact enumeration (GPLAN, 2020)**
- GPLAN (Shekhawat, Upasani, Bisht, Jain, BITS Pilani; arXiv 2008.01803) converts planar triangulated adjacency graphs into dimensionless rectangular floorplans (or orthogonal floorplans when no rectangular one exists) and dimensions them by linear optimization (dual simplex on horizontal/vertical st-graphs) under min/max room sizes; it reports generating 1,300 topologically distinct rectangular floorplans in 282.45 s and 256 orthogonal floorplans in 26.56 s; no public code URL is given in the paper — [GPLAN arXiv PDF](https://arxiv.org/pdf/2008.01803)

**Evolutionary / metaheuristic**
- Fan et al. (Automation in Construction 2023) automate the layout of modular high-rise residential buildings with a genetic algorithm using "two novel plane rotation models" as search spaces and a parameterisation of the modular flat encoded into chromosomes; constraints cover module dimensions and standardised flats, core sizing/code compliance, unit non-overlap and pedestrian flow; results are "similar to designers'" with many more alternatives; runtimes are not in the abstract, and the authors flag that subjective preferences are hard to model and CAD datasets are scarce — [Fan et al. 2023, ScienceDirect](https://www.sciencedirect.com/science/article/abs/pii/S0926580523002030)

**Procedural / grammar-based**
- Hektar (article dated 11 Aug 2026) describes a C# procedural generator in Grasshopper taking an apartment boundary polyline, façade, access point and required room list and producing many alternative layouts "in milliseconds", applied to "lamella structures, point houses and also for complex quarter structures"; outputs are framed as inspiration for architects, and the article gives few algorithmic details — [Hektar: Procedural housing floor plan generation](https://www.hektar.ai/post/procedural-housing-floor-plan-generation)
- A 2023/2024 Journal of Asian Architecture and Building Engineering paper applies shape grammar + BIM to generate mass modular housing for ShanLiChenJia village (Zhaoyuan, China) — [Tandfonline listing](https://www.tandfonline.com/doi/abs/10.1080/13467581.2023.2292081) (full text could not be fetched: HTTP 403; see Gaps)

**CP-SAT in practice on DXF geometry (open source, 2025/26)**
- plan2event-cpsat-v2 (GitHub) places event items on a venue DXF: ezdxf parses the DXF, Shapely (≥2.0) derives free-space polygons, pre-computed anchor points feed CP-SAT with `AddNoOverlap2D` for collisions and `AddAllowedAssignments` to keep placements inside the venue, objective = items placed + adjacency bonuses; a real 7.5 MB masterplan with 25 items was solved with zero violations in 35 s with optimality proven; stack: Python 3.12, ezdxf, shapely, numpy, scipy, matplotlib, ortools — [plan2event-cpsat-v2 on GitHub](https://github.com/Eli-AMAR/plan2event-cpsat-v2)

**OR-Tools CP-SAT primitives needed for the model**
- CP-SAT provides `NewIntervalVar(start,size,end)` (enforces start+size==end), `NewOptionalIntervalVar(...,is_present)`, `AddNoOverlap2D(x_intervals, y_intervals)` (axis-aligned rectangles must not overlap), `OnlyEnforceIf(literal)` (constraint active only when the literal conjunction is true), `AddBoolOr`, `AddMaxEquality`, `AddMultiplicationEquality` (usable for area = w·h), `AddElement`, `AddAllowedAssignments` (table constraint), and solver parameters `num_workers`, `max_time_in_seconds`, `enumerate_all_solutions`, plus `AddHint(var, value)` for warm starts — [OR-Tools CP-SAT Python reference](https://developers.google.com/optimization/reference/python/sat/python/cp_model)
- The CP-SAT Primer (d-krupke) is the standard practitioner guide covering modelling, advanced constraints (intervals, circuit), parameters, logs, LNS and benchmarking — [CP-SAT Primer](https://d-krupke.github.io/cpsat-primer/)

**In-session measurement (not a web source; script at `/tmp/claude-0/-home-claude/932662e5-b9fd-5d2e-ad48-991589ed92c8/scratchpad/cpsat_grid_layout.py`, OR-Tools 9.15.6755, 2 vCPUs, Sept 2026)**
- Model: rooms = integer rectangles (x, y, w, h in modules), `AddNoOverlap2D`, `Σ area == W·H` (exact tiling), min narrow side / min cells per room derived from the Turkish minimums (KQ4), adjacency "share ≥1 module of wall" via 4 enforcement literals per pair, every room adjacent to the hub (hol), windowed rooms must touch the envelope, hub touches the entrance side, objective = Σ |area − target|.
- Results: 8×6 modules (10.04 × 7.53 m, 75.6 m² gross), 6 rooms (salon, mutfak, 2 yatak, banyo, hol): feasibility OPTIMAL in 0.050 s; min-area-deviation OPTIMAL in 0.083 s; 10×8 modules (126 m²), 8 rooms (adds yatak3, WC): OPTIMAL in 0.159 s; single-thread enumeration of the 8×6 case returned 11,973 distinct feasible tilings in the 60 s cap without exhausting the space.
- Qualitative observation: without aspect-ratio or dimension caps the optimal-by-area solutions are legal but architecturally poor (e.g., a bedroom 2.51 × 7.53 m, a 18.9 m² hall), confirming the survey's "hand-crafted guidelines" caveat — scoring, not solving, is the bottleneck.

### Inferences
- Formulation sketch recommended for the company (derived from the cited CP-SAT API and the Co-Layout/GRIDS models; module = 125.5 cm):
  - Variables per room r: `x_r ∈ [0,W]`, `y_r ∈ [0,H]`, `w_r ∈ [wmin_r, wmax_r]`, `h_r ∈ [hmin_r, hmax_r]`, `a_r = w_r·h_r` (`AddMultiplicationEquality`), intervals `ix_r=(x_r,w_r)`, `iy_r=(y_r,h_r)`.
  - Hard: `AddNoOverlap2D(ix, iy)`; `Σ a_r = W·H` if the envelope must be fully tiled (drop it and add an "unassigned" filler room if verandas/L-shapes are allowed); min narrow side & min area (regulation, KQ4); windowed rooms touch the envelope (`AddBoolOr` over `x_r==0`, `x_r+w_r==W`, `y_r==0`, `y_r+h_r==H` with `OnlyEnforceIf`); adjacency/door feasibility: for each required pair, one of four "touch" literals (right-of / above with ≥1 module overlap) must hold; wet-room adjacency (banyo–mutfak share a wall) as a required pair; entrance side fixed (also breaks mirror symmetry).
  - Soft/objective: Σ weight·|a_r − target_r| + aspect-ratio penalties (bound `w_r ≤ k·h_r` and `h_r ≤ k·w_r` with k≈2 for bedrooms, or penalise via `AddMaxEquality`) + total interior wall length (fewer panels) + "hall area" penalty.
  - Panel-level rules (panel count, corner posts, window-in-panel-centre) are best expressed on the resulting wall segments in a post-solve validation pass rather than as solver variables (as Co-Layout does for doors/windows); truss direction can be a global boolean that selects which envelope side allows corner allowances.
- Runtime headroom is enormous for the company's scale (≤10 rooms, ≤80 cells): sub-second exact solves mean the generator can afford to enumerate hundreds of alternatives, score them with company heuristics, and show the dealer the top 3 — the pattern used by Laignel et al. (select three differentiated candidates) and GRIDS (multiple diverse solutions).
- Because CP-SAT enumeration explodes (>11,973 tilings in 60 s for a 48-cell grid), diversity should be forced explicitly (e.g., no-good cuts on room-order patterns, or "hub position"/"salon side" partitions) rather than by raw enumeration.
- A grid cell-assignment model (Co-Layout style) is only needed if non-rectangular rooms/L-shaped halls are required; for a panel house whose rooms are rectangles, the rectangle-interval model above is smaller, needs no big-M, and solves faster.

### Gaps
- No peer-reviewed source reports CP-SAT runtimes for exactly a 6×8 module residential grid; the numbers above come from an in-session experiment on a 2-vCPU sandbox and should be re-run on the company VPS.
- Co-Layout does not state per-case seconds; Laignel et al. do not name their CP solver; Merrell 2010's detailed cost terms and training-set size could not be extracted (PDF redirect loop).
- The shape-grammar mass-modular-housing paper (Tandfonline 2023/24) could not be fetched (403), so its rule set and implementation tools are unverified.

## Key Question 2 — Template-based parametric adaptation: nearest catalog plan, topology-preserving resizing, mirroring, module insertion; encoding 37 DXF plans as parametric templates; tools

### Takeaway
The proven non-ML route to "a plan that is not in the catalog" is case-based: store each catalog plan as a room-adjacency graph plus module-grid rectangles, retrieve the nearest case by program/envelope, then re-dimension it under min/max constraints with LP (GPLAN-style) or a CP-SAT model seeded with the template as a hint, using graph transformation rules (add/remove a room vertex while preserving the properly-triangulated planar property) when the program differs; ezdxf + Shapely + networkx cover the whole pipeline in Python.

### Cited Findings
- GADG (Wang, Yang, Zhang, Automation in Construction 2018) generates rectangular floor plans from existing layouts "while preserving room adjacency relationships": the input plan is converted to a dual graph (vertex = room, edge = adjacency), which must be Properly Triangulated Planar; an addition rule inserts a room vertex with up to 4 neighbours (boundary rooms: find a triangular face and remove a boundary edge; internal rooms: locate a quadrilateral cycle and remove the shared edge) and a subtraction rule removes a vertex and re-triangulates; an extended Bhasker–Sahni algorithm picks four corner vertices and converts the graph to rectangles; users can set max aspect ratios (e.g., 3:1) and move internal rooms to the boundary; plans with fewer than 10 rooms generate in under 5 ms; the case study imported a 7-room plan from IFC and supported an "unlimited generation-selection-refinement design cycle"; limitations: no directional constraints, no non-rectangular rooms — [Wang, Yang, Zhang 2018 (PDF)](https://personal.utdallas.edu/~kzhang/Publications/Automation18.pdf)
- GPLAN dimensions a topology by LP (dual simplex on st-graphs) minimising "the difference between width/height and their maximum bounds" subject to flow conservation and per-room min/max dimensions, and accepts "dimensionless layouts with rectangular or irregular boundaries" as input — i.e., it can re-dimension a given topology — [GPLAN arXiv PDF](https://arxiv.org/pdf/2008.01803)
- A 2019 CBR line of work ("Generation of Floor Plan Variations with Convolutional Neural Networks and Case-based Reasoning… unsupervised adaptation of room configurations") exists but is CNN-based, i.e., on the ML side — [ResearchGate listing](https://www.researchgate.net/publication/336877200_Generation_of_Floor_Plan_Variations_with_Convolutional_Neural_Networks_and_Case-based_Reasoning_-_An_Approach_for_Unsupervised_Adaptation_of_Room_Configurations_within_a_Framework_for_Support_of_Early)
- Honka's "standard model path" is template-based customization in practice: "a database of hundreds of ready-made, thoughtfully designed log homes", where "small-scale customisation of a ready-made house kit results in only small additional costs", e.g., "make the living room larger or change the place of the main entrance", arranged through local Honka representatives — [Honka standard model path](https://honka.com/en/dream-plan-build/planning-a-log-home/standard-model-path/)
- Kontio's catalog exposes the retrieval keys a template family needs: filters by gross living area 30–270 m², floors 1–3, bedrooms 1–5, over 100 models "that can be tailored to your individual needs"; no online configurator is offered — [Kontio models](https://www.kontio.com/en/models)
- GRIDS supports "auto-completion of partial designs" and returns multiple diverse solutions from a MILP, an approach directly reusable for "keep these rooms fixed, solve the rest" — [GRIDS](https://kashyaptodi.com/grids/)
- ezdxf 1.4.4 (May 2026, MIT, Python ≥3.10) reads/writes DXF R12–R2018 (read-only for R13/R14 and older), handles lines, lightweight polylines, text, dimensions, hatches, blocks/inserts, layers, entity queries; add-ons include `drawing` (PNG/PDF/SVG via matplotlib), `geo` (GeoJSON and Shapely interop) and `odafc` (DWG via ODA File Converter) — [ezdxf docs](https://ezdxf.readthedocs.io/en/stable/)
- plan2event-cpsat-v2 demonstrates the exact DXF→Shapely→CP-SAT→DXF round trip in Python (ezdxf parse, Shapely free-space polygons, CP-SAT placement, results written back as CAD blocks on dedicated layers) — [plan2event-cpsat-v2](https://github.com/Eli-AMAR/plan2event-cpsat-v2)
- A 2023 paper gives an algorithmic approach to extracting adjacency matrices from residential floor plans (useful for building the room graph from drawings) — [Frontiers of Architectural Research 2023 (ScienceDirect)](https://www.sciencedirect.com/science/article/pii/S2095263523000924)

### Inferences
- Template encoding for the 37 DXFs (practical recipe, derived from the tools above): (1) with ezdxf, read the room-boundary layer (LWPOLYLINE/closed polylines) and room-name TEXT/MTEXT; (2) build Shapely polygons, snap vertices to k·125.5 cm (assert residual < a few mm, otherwise flag manual clean-up); (3) derive rectangles in module units → matches the existing İş Emri JSON schema; (4) build a networkx graph with edges for polygons sharing ≥1 module of boundary, edge attributes "door" (from door blocks/INSERTs) and "wet" (shared plumbing wall); (5) record envelope W×H, entrance side, veranda side, truss direction, room list with (type, cells, w, h) and window panels; (6) store as one JSON per template plus a family index (m², room count, W, H, aspect).
- Retrieval: filter by room program (n_bedrooms, has_wc, veranda) then rank by |m²−target| and envelope aspect; mirroring (x→W−x) doubles the family for free and matters for entrance/veranda orientation.
- Adaptation ladder (cheapest first): (a) same topology, new W×H → re-dimension by LP/CP-SAT with the template's module rectangles as `AddHint` values (keeps the solution near the catalog look); (b) insert/remove one module column/row: stretch the rooms straddling that axis (topology-preserving); (c) program differs by one room → GADG-style add/subtract vertex, then re-dimension; (d) no template within tolerance → free CP-SAT model from KQ1 with template-derived soft targets.
- Grasshopper/Dynamo are unnecessary here: everything above is plain Python (ezdxf, Shapely 2, networkx, OR-Tools, scipy.optimize.linprog / HiGHS for the LP step) and runs headless on a VPS.

### Gaps
- GPLAN publishes no code; GADG's implementation is not public — the company would re-implement the rectangular-dual/re-dimensioning steps (moderate effort) or rely on CP-SAT re-dimensioning instead.
- No source documents how Honka/Kontio internally encode "standard model + modification" (grid, software), only the customer-facing description.
- No published, maintained open-source Python "floorplan template library" was found beyond GRIDS (UI layouts, MILP) and the CP-SAT DXF example; this is a build-it-yourself area.

### Takeaway

**Lessons from failures**

### Inferences

## Key Question 4 — Validation and rule encoding: company rules and Turkish minimum room dimensions as machine-checkable constraints; test strategy

### Takeaway
The Turkish "Planlı Alanlar İmar Yönetmeliği" gives crisp, machine-checkable minimums (narrow side and net area per room type, corridor width, door widths/height, mandatory room set), which translate cleanly into per-room lower bounds in module units (bedroom ≥2 modules ≈ 2.51 m clear only after subtracting panel thickness — check!); company panel rules are best encoded as a separate rule table evaluated on wall segments after solving, and validated by a "golden plan" regression suite built from the 37 catalog DXFs.

### Cited Findings
- Minimum piyes dimensions (Planlı Alanlar İmar Yönetmeliği, reported as Madde 31 in a 2020 summary): oturma odası narrow side 3.00 m / net 12.0 m²; yatak odası 2.40 m / 8.00 m²; mutfak (yemek pişirme yeri) 1.50 m / 3.30 m²; banyo (yıkanma yeri) 1.20 m / 3.00 m²; tuvalet 1.00 m / 1.20 m²; hol/koridor width ≥1.10 m; a combined bathroom–toilet must be ≥3.60 m² in units with 3 or fewer rooms; kitchen, rooms and bathrooms/toilets may not share the same ventilation shaft; accessibility standards apply — [Osman Midilli, "Yapı piyesleri ve ölçüleri" (17 Apr 2020)](https://osman.midilli.com/2020/04/17/yapi-piyesleri-ve-olculeri/)

### Inferences
- Module conversion (125.5 cm axis grid): regulation minimums are net (clear) dimensions, so the check is `k·125.5 − t_panel(s) ≥ min_clear`. Examples: bedroom 2.40 m → 2 modules = 251 cm axis-to-axis, leaving ~241 cm only if the two bounding panels together consume ≤10 cm of the room; with 10 cm panels on both sides (≈10 cm total from two half-panels) it is borderline, so the rule table should compute net width from the company's actual panel thickness rather than hard-coding "2 modules". Living room 3.00 m → 3 modules (376.5 cm) comfortably; kitchen 1.50 m → 2 modules (1 module = 125.5 cm fails); bathroom 1.20 m → 1 module (125.5 cm) only if net ≥120 cm, otherwise 2 modules; WC 1.00 m → 1 module OK; corridor 1.10 m → 1 module OK if net ≥110 cm.
- Rule taxonomy for the company (all checkable on the İş Emri JSON): (1) regulatory per-room bounds (above); (2) program rules (mandatory room set; wet rooms share a wall or a plumbing chase; kitchen adjacent to living); (3) access rules (each room has a door to hol/salon; door on a wall ≥1 module long and not in a corner panel; entrance door on the declared side); (4) light rules (each habitable room has ≥1 exterior panel with a window; window is in the panel centre); (5) panel rules (wall length = integer modules; corner posts at every outside/inside corner; max panel count per wall type; truss direction fixes which two envelope sides may carry the corner allowance/eave); (6) envelope rules (W, H even/odd module parity allowed; veranda depth in modules; gable ridge parallel to truss direction).
- Test strategy: (a) golden tests — every one of the 37 catalog plans, re-encoded to JSON, must pass the full rule set with zero errors (any failure means the rule is wrong or the plan is a documented exception); (b) mutation tests — perturb golden plans (shrink a bedroom by one module, remove a door, move a window into a corner panel) and assert the specific rule fires; (c) round-trip tests — JSON → DXF via the existing engine → re-parse → identical rectangles; (d) solver tests — for each catalog program and envelope, the generator must find a feasible plan within a time budget and the catalog plan itself must be feasible under the model (proves the model is not over-constrained); (e) property tests — random programs on random envelopes never produce overlaps, uncovered cells, or rooms below regulatory minimums.
- Severity tiers borrowed from Speckle (ERROR blocks quotation; WARNING needs engineer review; INFO informational) map naturally onto the dealer → engineer workflow in KQ5.

### Gaps

## Key Question 5 — Human-in-the-loop: dealer approves sketch → engineer checks; keeping an engineer's sign-off

### Takeaway
Every real-world workflow found keeps a licensed professional between the generated plan and production: in Turkey the permit set legally requires a mimar-signed architectural project and an inşaat mühendisi-signed structural project (Madde 57), US modular programs seal plans through third-party agencies and re-review any change, and dealers/consultants use explicit form-based sign-off gates (preliminary drawing request → customer print approval → permit prints → production authorization).

### Cited Findings
- Turkish permit set (Planlı Alanlar İmar Yönetmeliği Madde 57): mimari proje by a mimar (plans, sections, elevations), yapı aplikasyon projesi by a harita mühendisi, statik proje by an inşaat mühendisi with calculations, mekanik tesisat by a makine mühendisi (with heat-insulation report), elektrik tesisat by an elektrik mühendisi (can follow within 30 days), zemin etüdü by geology/geophysics/civil engineers; the "proje müellifi" bears responsibility for compliance; İmar Kanunu Madde 28 & 38 require professionals to work within their specialization — [Gayrimenkul Mevzuatı summary](https://gayrimenkulmevzuati.com/insaat-ruhsati-alinmasi-icin-gereken-projeler-nelerdir/)
- Custom Modular Direct (US dealer/consultant) uses a 9-step, form-gated flow: plan selection → "Form #200 Preliminary Drawing Request" (design staff draws, customer reviews/modifies) → signed purchase agreement with deposit → "Form #202 Final Print Approval" → "Form #201 Permit Print Request" for state-approved blueprint copies → delivery procedure sheet → "Form #500" production authorization with a 10% start deposit → lender COD letter → delivery — [Custom Modular Direct process](https://responsive.modulardirect.com/HowOurProgramWorks.php)
- North Carolina modular approval: manufacturers submit a QC manual and complete plans to a third-party certification agency ($1,000 fee + $1,000 state review); "all engineering designs and calculations for components or systems not covered by recognized prescriptive tables must be sealed by a North Carolina registered design professional"; approval is a "systems approach" — after certifying the first unit, additional models within the approved package need only third-party plan review; changes to approved plans are re-reviewed and "no NC Modular Stamps will be issued for the model in question until corrections are received, reviewed, and approved" (major revisions $500) — [NC OSFM modular manufacturer approval](https://www.ncosfm.gov/manufactured-bldg/modular-buildings/modular-manufacturer-approval-procedures)
- Cover: designs with fixed pricing arrive within days, but Cover's own team handles permitting with a refund guarantee, i.e., professional review precedes manufacturing — [Cover process](https://buildcover.com/our-process/)
- Boxabl: order fee + deposit, then a "virtual initial site check and preliminary feasibility report", and installation by trained "preferred BOXABL installers" — [Boxabl FAQ](https://www.boxabl.com/faq)
- Honka: modifications are arranged with local representatives and "every detail of your house package is marked and documented" before packaging — [Honka](https://honka.com/en/dream-plan-build/planning-a-log-home/standard-model-path/)
- Prefabrik Yapı performs static calculations in-house when detailing custom projects — [Prefabrik Yapı](https://www.prefabrikyapi.com/)
- The 2025 layout review notes optimization-based methods "usually require post-processing and involve human interaction", which it frames as designer control — [Liu et al. 2025 review](https://iccvm.org/2025/papers/s7p5-532-cvmj.pdf)
- Speckle Automate runs rule checks automatically when a model version is published and reports ERROR/WARNING/INFO — a mechanical pre-check before human review — [speckle-automate-checker](https://github.com/specklesystems/speckle-automate-checker)

### Inferences
- Recommended gate design for the company: (G0) generator output + automatic rule report (ERROR/WARNING/INFO) → (G1) dealer confirms program/orientation with the customer on the sketch (no engineering authority; "ön eskiz — onaylı proje değildir" watermark) → (G2) company architect/engineer reviews WARNINGs, panel schedule and truss direction, signs the İş Emri (digital signature/hash of the JSON) → (G3) permit set produced by the registered mimar/inşaat mühendisi as required by Madde 57. The NC "systems approach" suggests pre-approving the parametric family (rules + panel catalog) once, so that per-house review focuses only on deviations (WARNINGs) rather than re-checking everything.
- Because the generator is deterministic, the JSON İş Emri plus rule-set version can be hashed and stored with the engineer's approval, giving traceability of exactly which rules a plan was checked against — an audit trail similar to state modular stamps.

### Gaps
- No Turkish-specific source was found describing how prefab firms run dealer-level pre-approval (bayi ön onayı) versus company engineering sign-off; only the legal project-signature requirements are documented.
- No source quantifies how much review time a rule-based pre-check saves in prefab practice (Speckle's Pomerleau case claims 90% faster QA/QC checks, but that is equipment tracking, not house plans — [Speckle customer story](https://speckle.systems/customer-stories/pomerleau-achieves-90-faster-equipment-tracking-and-qa-qc-checks-speckle/)).
